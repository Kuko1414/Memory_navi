🤖 本地 VLM 空间智能体 — 项目计划书 v3.0

📅 报告日期：2026年6月18日（v3.0 修订） 📝 版本：v3.0（回归双模型分工：大模型记忆 + 小模型执行） 📎 前置版本：v1.0（2026-06-04）· v2.0（2026-06-16）
🔄 v3.0 修订说明：v2.0 把云端降级为"异常兜底"、用 Qwen 自评置信度触发升级。实测暴露两个问题——(1) 两个模型共同决策时任务逻辑易冲突；(2) 模型对自身错误无感知（过度自信），置信度触发不可靠，该升级时不升级。v3.0 回归学术版的核心主张：大模型与小模型按职责分工，而非共同决策——云端大模型负责精确记录记忆（在探索/近距/交互时刻，由结构化条件触发），本地 Qwen3-VL-8B 负责基于语义拓扑的高效执行。记忆采用"词典式"按需检索（拓扑导航到位 → 再查局部语义），区别于 Embodied-RAG 的全局地图。代码层继续承担安全与空间计算；Supervisor 调度形态待定（确定性代码 or 小模型）。

一、项目概述

一句话定位：构建一个本地-云端协作的具身 VLM 智能体——云端大模型精确构建记忆、本地 Qwen3-VL-8B 高效执行，记忆以"词典式"按需检索（拓扑导航 → 局部语义精查），让轮式机器人在室内语义导航任务中可靠运行。

1.1 核心问题

传统 Navigation Stack 在长程任务中缺乏对空间的语义理解能力。纯 VLM（如 Gemini API）虽然理解力强，但延迟高（1–3s）、无持久记忆。VLA 模型偏重端到端执行，缺乏可审计的结构化记忆。而多模型本地部署方案对硬件要求过高——实测单张消费级显卡无法同时运行两个 VLM。

核心挑战：如何让云端大模型与本地小模型各取所长、按职责分工，而不是让两个模型"共同决策"（共同决策会引发逻辑冲突，且模型对自身错误无感知，靠置信度自评切换并不可靠）？具体而言——大模型应在何时、记录什么样的记忆，才能让小模型以最少的信息（拓扑优先、局部语义按需）高效完成任务，实现高信息利用率？同时，能写死的安全阈值、能算出来的坐标、能走 Nav2 的避障，仍交给确定性代码而非模型。

1.2 学术贡献定位

贡献类型内容证据要求
A. 新方法 提出 Spatial Token Graph (STG) 的"词典式"按需检索——双层级空间表征：上层语义拓扑图（房间连通性、路径方向）供远距导航，下层 JSON 结构化记忆（物体、置信度、空间-时间）作为"词典条目"供近距精查。执行任务时不通读全局地图，只在需要时翻对应词条，从而提高信息利用率（区别于 Embodied-RAG 的全局地图式利用） 与"全局地图式检索"baseline、无结构记忆 baseline 的信息利用率与耗时对比
B. 新系统 构建 大模型记忆 + 小模型执行的职责分工式 具身智能体：云端大模型在结构化触发时刻（进入新区域 / 近距交互）精确记录记忆，本地 Qwen3-VL-8B 基于拓扑高效执行，代码层承担安全与空间计算。按职责分工而非共同决策，规避逻辑冲突与"模型不自知错误" 多轮长程任务实验：云端调用随轮次下降的趋势；与"共同决策/置信度升级"方案的对比

三、核心组件说明

3.1 双层推理架构（本地执行 + 云端记忆）

两个模型按职责分工、不共同决策：本地 Qwen3-VL-8B 是执行者（拓扑导航、Skill 执行），云端大模型是记忆作者（在结构化触发时刻精确记录记忆）。代码层承担安全与空间计算。这从根上规避了"两模型抢同一决策导致逻辑冲突"与"模型不自知错误"两个问题。

3.2 Supervisor 调度机制（形态待定）

Supervisor 负责 Skill 调度与云端记忆触发。当前设计为确定性数值比较（只看结构化数值，不评估语义），但其最终形态待定——可能保持为确定性代码，也可能下沉为一个轻量小模型，下一轮专门讨论。以下为当前规则草案。

输入结构

state = { "robot": { "pose": (x, y, yaw), # 来自 /odom "lidar_min_m": 0.42, # 最近障碍物距离 "sensors_ok": True, # 传感器健康汇总 "battery": 0.85, }, "semantic_map": { "areas": [ {"id": "kitchen", "visited": True, "last_seen": "2026-06-16T10:20"}, {"id": "corridor", "visited": True, "last_seen": "2026-06-16T10:18"}, {"id": "room_b", "visited": False, "last_seen": None}, ], "objects": [ {"name": "fridge", "area": "kitchen", "confidence": 0.92, "last_seen": "..."}, ], "connectivity": [...], "hazards": [...], }, "task": { "skill": "explore", # 当前 skill "target": "room_b", # 当前目标 "retry_count": 0, "entered_new_area": False, # 刚进入未记录区域 → 触发云端记忆 }, "user_command": "探索完所有房间后告诉我每个房间有什么", }

六条决策规则

0 安全——最高优先级，不经过任何判断：
lidar_min_m < 0.15 OR sensors_ok == False → EmergencyStop
这条规则覆盖报告 v1.0 中的 Level 0 硬刹车，但不依赖任何模型仲裁。
1 进入新区域 / 近距交互——触发云端记忆：
entered_new_area OR skill == "inspect" → DispatchCloud(record)
由结构化条件触发云端大模型精确记录记忆，不依赖模型自评置信度（模型对自身错误无感知，置信度触发不可靠）。
2 重试上限——保守暂停：
retry_count >= 3 → SafePause + Notify
同一任务连续 3 次失败（导航未到达、物体未识别），转入保守暂停并通知，不让模型反复试错。
3 未探索区域——切换到 explore skill：
exists(area.visited == False) → SwitchSkill("explore")
选择距离当前位置最近的未探索区域作为目标。Qwen 收到 explore prompt + 目标坐标。
4 用户导航目标——切换到 navigate skill：
user_goal IN semantic_map.areas → SwitchSkill("navigate")
从用户指令中解析目标（"去厨房"→"kitchen"），查拓扑图计算路径方向，下发给 Qwen。
5 任务完成：
all(area.visited == True) → TaskComplete
所有已知区域均已访问，汇总语义地图返回给用户。
🔑 为什么不把 Skill 切换交给 Qwen 自己判断？
LLM 不擅长元决策。切换 Skill 的条件全部是确定性比较（"visited == False""retry >= 3""confidence < 0.6"），用 Python 写比让模型猜更可靠、更快（<1ms vs >500ms）、且零幻觉风险。

3.4 双层级空间记忆

空间记忆由云端大模型写入、本地 Qwen 读取，是两者分工的交汇点，也是 Supervisor 决策的核心数据源——visited 字段决定 explore skill 触发，connectivity 拓扑图决定 navigate 的路径方向。检索是"词典式"：远距只取拓扑，近距才翻出对应区域的物体词条。

四、工程实现流程

📐 设计原则：每个阶段有明确的完成标准（Definition of Done）和阶段验证实验。不设定具体日期，按验证通过顺序推进。核心假设在阶段 1 末进行关键决策。

阶段 1：最小原型验证

#任务产出完成标准
1.1 确认硬件环境：vLLM + Qwen3-VL-8B（FP16）推理延迟 < 500ms，显存占用实测 推理基准表 8B FP16 稳定运行，显存 ~24 GB，免量化（保证 function calling 稳定）
1.2 编写 spatial_memory.py：JSON Schema 定义 + CRUD API + 拓扑图 BFS 查询 memory.py + 单元测试 所有 CRUD 操作通过测试；拓扑路径查询正确返回最短路径
1.3 编写 safety_layer.py：LiDAR 订阅 + 阈值急停 + 传感器心跳检测 safety_layer.py LiDAR 模拟 <0.15m → <10ms 发出急停信号
1.4 编写 supervisor.py：6 条规则 + Skill 分发框架 supervisor.py + 状态日志 模拟 state 输入 → 输出正确的 Skill/EmergencyStop/DispatchCloud
1.5 最小 A→B→A 实验：2 房间 + 走廊，取送任务 10 轮。对比 baseline（纯 Qwen 无记忆）vs 本系统（Qwen + JSON 记忆 + Supervisor） 实验数据 CSV 10 轮完成；数据完整；对比分析报告
⚠️ 阶段 1 关键决策点：如果最小原型不能证明「JSON 空间记忆 + Supervisor 状态机减少了 Qwen 推理次数和导航时间」，则暂停后续阶段，重新评估架构方向。这是整个项目最核心的假设——结构化记忆是否让单模型方案可行。

3.2 记忆工具封装：update_json、query_topology、mark_area、get_unvisited 等 tools/memory_tools.py Qwen 可通过 FC 读写语义地图；Supervisor 自动同步
3.3 交叉传感器验证：RGB 检测物体 + Depth 确认距离 + LiDAR 确认障碍 → 三方才写入 JSON verification.py 单一传感器误判不污染记忆
3.4 置信度时间衰减：> 24h 未确认的信息自动 confidence × 0.95 memory 模块内置 衰减后 confidence < 0.5 触发 Supervisor 的 inspect skill
3.5 验证实验：3 房间环境下 5 轮探索→记忆写入→导航验证。检查 JSON 记忆质量（精确度、召回率） 记忆质量报告 物体识别 precision ≥ 0.7；区域类型分类 accuracy ≥ 0.8

阶段 4：异常处理与安全加固

#任务产出完成标准
4.1 Nav2 集成：全局规划器 + 局部避障 + 重规划逻辑 nav2_bridge.py Qwen 下发目标点后 Nav2 自主完成路径规划与避障
4.2 降级策略：安全层独立进程运行，Qwen 进程崩溃不影响急停 多进程架构 kill Qwen 进程 → 机器人保持静止，safety_layer 仍在运行
4.3 Token 预算控制：上下文窗口管理（关键帧 + JSON 分级检索 + 滑动窗口） context_manager.py 10 轮任务后 prompt < 32K tokens
4.4 验证实验：注入故障（Qwen 崩溃、LiDAR 遮挡、未知物体、死胡同）。验证系统在每种场景下的行为 故障注入测试报告 所有注入故障正确处理：不碰撞、不回退到错误状态、合理降级

训练策略 待定

当前立场：Qwen3-VL-8B-Instruct 原生支持 function calling 和视觉理解，prompt engineering 可以覆盖当前需求（语义标注、物体识别、导航决策）。暂不进行模型微调。

触发微调的条件：若阶段 2/3 实验表明 Qwen 在以下任一场景持续失败——(a) 房间类型分类 accuracy < 0.6；(b) function calling 格式错误率 > 20%；(c) 置信度长期 < 0.6 导致 Claude 调用频率 > 30%——则启动 LoRA 微调计划。

若启动微调：使用阶段 1–3 采集的 (图像, 指令, 工具调用) 三元组构建训练集；BC warmup → GRPO RL 路径保留 v1.0 的设计；但微调对象降为单个 Qwen3-VL-8B（而非 v1.0 的 7B Orchestrator + 3B Fast VLM）。

九、总结

一句话总结：v3.0 的核心赌注是——大模型与小模型按职责分工而非共同决策：云端大模型在结构化时刻精确构建记忆，本地 Qwen3-VL-8B 基于拓扑高效执行，记忆以"词典式"按需检索；安全与空间计算交给确定性代码。如果这个架构在阶段 1 验证通过，将证明多 agent 在单机器人上的优势来自"各取所长"，而非共同决策。

最小验证（阶段 1）：A→B→A 的 10 轮实验是唯一关键决策点。核心指标不是绝对性能，而是趋势——JSON 记忆积累后，Qwen 推理次数和任务耗时是否持续下降。

v2.0 → v3.0 的转变：v2.0 把云端当"兜底"、靠模型自评置信度升级，实测发现共同决策易冲突、且模型不自知错误。v3.0 改为按职责分工——云端专做记忆、本地专做执行、代码专做安全与计算，三者边界清晰、互不抢决策；远距用拓扑、近距才查语义词典，信息利用率高。
