# /report — 工作区智能报告生成器

> 此命令是 `@report` 技能的核心定义。当用户输入 `/report <参数>` 时，Claude 会加载此 Prompt 并严格按流程执行。

---

## 阶段 0：输入解析

用户输入格式：`/report <日期范围> [可选说明]`

### 0.1 语言检测
- 用户 prompt 为**中文** → 报告全文使用**简体中文**
- 用户 prompt 为**英文** → 报告全文使用**English**
- 语言决定了报告的章节标题、说明文字、图表标注等一切内容

### 0.2 输出格式检测
- prompt 中含 `html` / `HTML` → **HTML 报告模式**
- prompt 中含 `md` / `markdown` / 无格式关键词 → **Markdown 报告模式**
- 如果用户未明确指定格式，**默认使用 Markdown**

### 0.3 日期范围解析

**规则：**
- 格式：`M.D-M.D` 或 `M.DD-M.DD`（如 `1.21-3.1` = 1月21日 → 3月1日）
- 年份默认使用**当前年份**（从系统日期获取）
- 结束月份必须 ≥ 开始月份（不处理跨年）
- 如果结束月份 < 开始月份，提示用户"日期范围似乎有问题，是否跨年了？请明确指定年份"

**解析示例（假设当前为 2026 年）：**
| 输入 | 解析结果 |
|------|----------|
| `1.21-3.1` | 2026-01-21 → 2026-03-01 |
| `3.14-4.15` | 2026-03-14 → 2026-04-15 |
| `12.1-12.31` | 2026-12-01 → 2026-12-31 |

## 阶段 1：数据采集

### 1.1 读取 MEMORY.md

使用 Read 工具读取 `MEMORY.md`。搜索格式为 `## MMM.DD, YYYY` 的日期标题（英文月份缩写）：

```
## Jan.21, 2026  ← 匹配
## Mar.14, 2026  ← 匹配
```

**日期匹配逻辑：**
1. 解析 MEMORY.md 中所有 `## <Month>.<Day>, <Year>` 格式的标题
2. 筛选出落在用户指定时间范围内的条目
3. 提取每个日期标题下的所有内容（直到下一个 `##` 标题或文件末尾）

### 1.2 有效性检查

- ✅ **找到了匹配条目** → 继续阶段 2
- ⚠️ **没找到任何条目** → **必须**向用户确认：
  > "在 MEMORY.md 中没有找到 `{dateRange}` 期间的记录。请确认：1) 日期范围是否正确？2) 这些日期的变更记录是否还未写入 MEMORY.md？"
  - 不要擅自编造数据，等待用户回复

### 1.3 辅助数据采集（HTML 模式需要）

当输出格式为 HTML 时，额外采集以下数据：

1. **读取 PROCESS.md** — 获取 Step 1-10 的当前状态（done / in progress / planned），用于生成可折叠的进度步骤面板
2. **读取 ARCHITECTURE.md** — 获取 ROS2 Topic 列表、Node 描述、硬件信息，用于生成可折叠的硬件/系统架构面板(根据进度或更新决定是否需要，项目初期/节点或硬件有更新需要，后期未更新不需要)
3. **扫描 data/experiment/ 目录** — 检查是否有实验数据可用：
   - `group*/` 下的 `*task*.md` 文件（实验说明/结果）
   - `group*/` 下的 `*pose*.log` 文件（轨迹数据）
   - `group*/` 下的 `*conversion*.log` 文件（转换日志）
4. **扫描 data/log/ 目录** — 获取最近的调试日志

## 阶段 2：报告生成 — Markdown 模式

### 报告结构

```markdown
# 阶段报告：[根据内容自动生成标题]

> 报告时间：YYYY年M月D日 | 报告范围：{开始日期} — {结束日期} 工作进展

---

## 一、总体概述
[一段话概括本阶段的主要成就和方向变化，2-4句话]

## 二、按时间线的工作内容
[按日期分组，每天一个子章节]

### M月D日：[当日主题概括]
- [具体变更1] — [原因/效果]
- [具体变更2] — [原因/效果]
...

## 三、关键技术决策
[本阶段做出的重要架构/方向决策，每个决策包含：背景 → 决策 → 影响]

## 四、当前系统状态
[引用 PROCESS.md 的 Step 状态，用表格呈现]

| Step | 名称 | 状态 |
|------|------|------|
| Step 1 | ... | ✅ / 🔄 / 📋 |
...

## 五、遇到的问题与解决方案

| 问题 | 严重程度 | 解决方案 | 状态 |
|------|----------|----------|------|
| ... | 🔴/🟡/🟢 | ... | ✅/🔄/📋 |

## 六、下阶段计划
[接下来要做什么，按优先级排列]

## 七、总结
[一段话总结，呼应概述]
```

### 编写原则
- **重内容轻形式**：重点呈现思想/架构/方向的变化，而非流水账
- **量化**：尽可能给出数据（提交数、修改行数、实验成功率等）
- **关联**：将分散的变更串联成有逻辑的叙事
- **诚实**：列出未解决的问题和风险

## 阶段 3：报告生成 — HTML 模式

### 3.0 ⚠️ 第一步：读取 HTML 模板（必须执行）

**在生成任何 HTML 代码之前，必须先用 Read 工具读取模板文件：**

> 📁 **模板路径：** `.claude/templates/report/report_template.html`

该模板包含：
- 完整的 CSS 样式系统（工程文档风格、CSS 变量、响应式布局）
- 所有图表组件（柱状图、折线图、饼图、甘特图、Canvas 图）的 HTML 骨架 + CSS 动画
- Intersection Observer 滚动触发引擎（进出视野自动重播/重置）
- 占位符标记（`{{...}}`），大模型替换为实际内容

### 3.1 总体风格
- **工程文档风格**：延续现有 Markdown 报告的专业感，HTML 只增强可视化
- 代码块使用等宽字体 + 深色背景 (#1e293b)
- 表格使用斑马条纹
- 可折叠面板（`<details>`）用于硬件/ROS Topic/Step 详情
- 响应式设计，适合 16:9 投影

### 3.2 ⚠️ 图表规则（核心约束）

**所有图表必须使用 Intersection Observer 滚动触发：**

1. **禁止静态图表**：不要使用页面加载就显示完毕的静态 SVG/CSS 图表
2. **图表容器**：每个图表必须包裹在 `<div class="chart-wrapper">` 中
3. **动画类名**：
   - SVG 柱状图：每个柱条加 `class="lazy-bar"`
   - SVG 折线图：路径加 `class="lazy-line"`，数据点加 `class="lazy-dot"`
   - SVG 饼图：每个扇区加 `class="lazy-pie"`
   - Canvas（Chart.js）图表：包裹在 `<div class="lazy-canvas-container">` 中
4. **触发机制**：页面底部的 Intersection Observer 脚本自动监听所有 `.chart-wrapper`，进入视野时加 `.visible` 类触发 CSS 动画，离开视野时移除 `.visible` 重置动画
5. **阈值**：`threshold: 0.25`（图表 25% 进入视野即触发）

### 3.3 数据图表选择

根据 data/ 的实际内容判断最合适的图表类型：

| 数据类型 | 推荐图表 | 实现方式 |
|----------|----------|----------|
| 实验成功率（多组对比） | 分组柱状图 | SVG `lazy-bar` 或 Chart.js |
| 轨迹数据（pose log） | 2D 散点/折线图 | SVG `lazy-line` + `lazy-dot` |
| 时间进度（Step 完成时间线） | 甘特图 | 纯 CSS `.gantt-bar` |
| 路径平滑度（deviation 变化） | 折线图 | SVG `lazy-line` |
| 深度有效率对比 | 柱状图 | SVG `lazy-bar` |
| 比例分布（任务状态等） | 饼图/环形图 | SVG `lazy-pie` |

**注意：**
- 模板中已包含所有图表类型的完整 CSS 动画定义，**不要重复定义**
- 使用 Chart.js CDN（`cdn.jsdelivr.net`，已在模板 `<head>` 中引入）
- 图表数据从实际文件中提取，如果数据不足以生成有意义的图表，**跳过该图表并注明原因**
- 图表下方必须用 `.chart-note` 标注数据来源

### 3.4 必备内容组件

#### A. 可折叠进度面板（基于 PROCESS.md）
使用 `<details>` + 带复选框的 `.step-list`：
```html
<ul class="step-list">
  <li>
    <input type="checkbox" class="step-check" checked disabled>
    <span class="step-label">
      <span class="step-name">Step 1: 路径生成与基础跟踪</span>
      <span class="step-desc">创建 Generate_Path 节点…</span>
    </span>
    <span class="badge badge-done">已完成</span>
  </li>
</ul>
```

#### B. 可折叠硬件/系统架构面板（基于 ARCHITECTURE.md）
```html
<details>
  <summary>🖥️ Computing Device: Nvidia Jetson Orin Nano (8GB)</summary>
  <div class="detail-content"><p>GPU: 1024-core Ampere, 32 Tensor Cores, 40 TOPS INT8</p></div>
</details>
<details>
  <summary>📡 /odom — Odometry (nav_msgs/Odometry)</summary>
  <div class="detail-content"><p>Provides robot pose + twist. Core data source for odom frame.</p></div>
</details>
```

#### C. 问题/风险表格
使用标准 `<table>` + 严重程度徽章。

## 阶段 4：文件输出与命名

### 4.1 输出路径
- 所有报告保存到 `Report/` 目录
- 如果 `Report/` 不存在，创建它

### 4.2 命名规范
```
<day>_<month>_<yy>_report.<ext>
```
- 日期为**报告生成当天**（不是报告覆盖的时间范围）
- 示例：2026年6月1日生成的报告 → `1_6_26_report.md` 或 `1_6_26_report.html`

### 4.3 文件冲突
- 如果同名文件已存在 → 覆盖（因为同一天只应有一份报告）
- 如果需要在同一天生成 MD + HTML 两份 → 后缀自动区分（`.md` / `.html`）

### 4.4 完成后通知
生成完成后，告知用户：
- 📄 文件已保存到：`Report/<文件名>`
- 📊 报告覆盖的时间范围
- 📝 报告的字数/章节数
- 💡 如果报告是 HTML 且用户之前提到要 push 到 GitHub，提醒用户：
  > "HTML 报告已生成。如需推送到 https://github.com/Kuko1414/Group_report，请审阅后告诉我，我会帮你执行 push。"

## 阶段 5：特殊场景处理

### 5.1 简陋模式（无额外说明）
用户只输入 `/report 1.21-3.1` 或 `/report md 1.21-3.1`：
- 使用默认 Markdown 模板
- 包含 MEMORY.md 中的所有日期条目
- 不做深度数据分析和图表

### 5.2 带特殊要求
用户输入 `/report 1.21-3.1 html 重点分析PID调参过程`：
- 在标准 HTML 报告基础上
- 额外增加 PID 调参的专项分析章节
- 如果有对应的 pose log，绘制调参前后轨迹对比图

### 5.3 带草稿/模板要求
用户输入 `/report 1.21-3.1 html 按照我的思路模板写报告 + “提供1_6_26_report.md”`：
- 在标准 HTML 报告基础上，但是内容要额外参考用户提供的md/html文件
- 如果格式相同，可以直接在该文件基础上更改，如果格式不同，以提示词中要求的为准
- 额外增加 PID 调参的专项分析章节
- 如果有对应的 pose log，绘制调参前后轨迹对比图

### 5.4 MEMORY.md 中无记录
- **绝不编造数据**
- 明确告知用户未找到记录
- 提示可能的日期格式错误或遗漏
